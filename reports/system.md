## 2. ★CSV→Shopify 反映基盤（最優先タスク）

### 作ったもの

`scripts/artist-csv-sync.mjs`（check / pull / plan / apply）＋ `docs/手順_作家CSVとShopifyの突合と反映.md`

### ★★ 最重要の警告：いま機械的にCSVを流すとデータが壊れます

代表決定は「正本＝CSV」ですが、**実測するとShopify側にしか無い正しい訂正があります**。実例＝**深山龍洞**：

| 項目 | CSV（正本のはず） | Shopifyライブ（実際は正しい） |
|---|---|---|
| name_en | Fukayama Ryudo | **Miyama Ryudo** |
| 呼称 | 書家／漢字 | **書家／かな** |
| 出身地 | 調査中 | **淡路（兵庫県）** |
| statement | 一東書道会を率いた漢字書の書家 | **淡路に生まれ、神戸で活動したかな書の書家。** |
| よみがな | ふかやま りゅうどう | **みやま りゅうどう** |

CSV側が別人の情報と取り違えている疑いが濃厚です。**このまま流すと正しい情報が誤りで上書きされます。**

**提案する初回手順**：①差分を出す（済）→ ②36件を1件ずつリサーチTが判定 → ③**ライブが正しいものはまずCSV側を直す** → ④CSVが正しいものだけ反映。②③を省くと正本化の初回作業そのものがデータ破壊になります。

### 実測結果

```
CSV 596行 / Shopify 597件 → 全596名が照合できた
実質的な差分: 36件（bio_ja 12 / masterworks_text 10 / death_year 4 / 他）
区切り記号のみの差: 4件（「日展・書海社」と「日展、書海社」等）
CSV空でスキップ: 127件
スラグ相違: 4件（報告のみ）
Shopifyのみに存在: 1名（鈴木千賀子＝存命作家・想定内）
```

### 対応表は「名前の似ている順」ではなく実データの一致率で確定させました

**Shopifyの `genre` はCSVの「呼称」（100%一致）であって「肩書き」（69%）ではありません。**「ジャンル」は `category`（100%）です。名前で推測していたら596名全件を壊すところでした。

照合でも実測が効きました。Shopifyは「鈴木 千賀子」、CSVは「鈴木千賀子」と姓名間の空白が違い、素直に突き合わせると**592名が「CSVにしか無い」と誤判定**されました。

### 安全設計

- `apply` は「計画ファイル」「`--yes`」「`SHOPIFY_ALLOW_WRITE=1`」の**3つが揃わないと動きません**
- **既存レコードの更新のみ**。新規作成・削除は一切しません
- **楽観ロック**：計画作成後にライブが変わっていたら**上書きせず停止**
- **同名が複数なら対象から外す**（配列順で選ばない）
- **1件ごとに独立クエリで読み戻し照合**＋**更新前後の全フィールドをJSONLに記録**（ロールバック材料）
- `name_ja`（照合キー）と `handle`（URLスラグ）は変更しません

### URLスラグとリダイレクト（(b)）

スラグ相違4件はいずれも読み違いの訂正（例：吉田稔郎 `minoru-yoshida`→`toshio-yoshida`）。

**変えるなら必ず「①旧URL控え→②handle変更→③即座に301リダイレクト作成→④curlで301を実測→⑤リダイレクトは恒久的に残す」の順。** 印刷済みQRがある作家は特に慎重に。**変えない判断も十分あり得ます**（URLは利用者に見えにくい）。

なお深山龍洞は `fukayama-ryudo` がHTTP 200で生存、`miyama-ryudo` は404。ただし上記のとおりCSV側が誤っているため、変更の要否判断が先です。

## 3. 全作家ページの空画像枠 → **バグではありませんでした**

実測の結果、`× ‹ › ![](<>) …` の正体は**ライトボックス（拡大表示）の雛形**でした。

| 確認項目 | 結果 |
|---|---|
| `src=""`（空文字） | **0件**（`src`属性そのものが無い） |
| 画面に見えているか | **見えていない**（`display:none` を live CSS で確認・実ブラウザで幅0高0） |
| 余計なHTTPリクエスト | **発生しない**（`src`属性が無い`<img>`はフェッチしない。再取得が起きるのは`src=""`の場合だが0件） |

**あえて実装を見送りました**。①実害ゼロを実測で確認 ②当該ファイル（`atspect-artist-detail.liquid`）は**制作Tが編集中で、調査中にもライブが変わった**ため。利用者に見える利益ゼロの変更で他ターミナルの作業に割り込むのは割に合わないと判断しました。条件分岐で包む案は提出済みです。

## 4. 作家ページ多言語化の設計（実装は指示待ち）

**固定文言**（ラベル・見出し・ボタン）と**作家ごとのデータ**を分けて解きます。

- **固定文言** → 既存のdata-langスパン方式をそのまま使う（15〜20文言×8言語）。Shopify標準の翻訳機能を使うと**多言語システムが二重になる**ため推奨しません
- **作家ごとのデータ** → ★`genre_en` `location_en`… と**言語別フィールドを49個増やすのは不可**（定義は既に40フィールド）。**既存の `artist_i18n`（JSON）を正式なi18nコンテナとして拡張する**のが正解。未翻訳は「キーが無い＝日本語にフォールバック」で自然に扱えます

| 段階 | 内容 | 見積り | 崩れリスク |
|---|---|---|---|
| Phase 1 | 固定文言の8言語化 | **0.5〜1日** | 低 |
| Phase 2 | `artist_i18n`スキーマ＋汎用snippet＋1名で実証 | 1日 | 中 |
| Phase 3 | 596名分の翻訳投入 | 翻訳量が支配的・数日〜 | 低 |

**推奨＝Phase 1 だけ先に**。英語利用者が感じる「日本語のまま」の大半はラベル・見出し・ボタンで、費用対効果が圧倒的です。

## 6. Codex独立レビューで自分の実装を修正しました

**重大な指摘を受けて即日直しました**：①計画作成後にライブが変わっても上書きしていた→**楽観ロックを実装** ②同名複数でも先頭を更新していた→**対象から外す** ③`ALLOW_WRITE`が恒久スイッチ化していた→実行時承認を可能に ④復旧証跡が無かった→**更新前後をJSONL記録** ⑤読み戻しがmutation戻り値だった→**独立クエリで再取得**。

Codexが確認してくれた点：`&#32;`は妥当／`metaobject:{fields:}`は部分更新で**未送信フィールドは消えない**（★`values:`に変えると全消去。将来のリファクタ厳禁としてコメント固定）／空画像枠の見送りは妥当。

**申し送り**：CSVの「空欄」に未調査と明示削除の2つの意味があり、**ライブの誤情報を消せません**。CSVに三状態を持たせる設計がリサーチTとの取り決め事項です。長期的には照合キーを`name_ja`ではなく不変IDにすべきです。
