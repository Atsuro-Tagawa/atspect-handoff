# 書き込み安全（あつぺくと作家データ）

**この経路以外でライブを書き換えない。** 手で本文を転記しない（写し崩れが起きる）。

---

## いつ発動するか

- 作家の訳文・データを**ライブへ反映する**とき（是正・追記・訳し直しの適用）
- `SHOPIFY_ALLOW_WRITE=1` を使うとき
- **読み取りだけの走査・検品には不要**（`_readonly-*` は書き込まない）

## 手順（この順を崩さない）

### ① 置換表を書く（`from` / `to` を1件ずつ）

```json
{ "reason": "…", "enteredBy": "…", "enteredDate": "YYYY-MM-DD",
  "patches": [ { "handle": "…", "lang": "zh_cn", "field": "bio", "from": "…", "to": "…" } ] }
```
`field` は `bio` / `statement` / `viewpoint` / `groups` / `role` / `location` / `collection` / `masterworks`。

### ② 指示書を生成する＝★ここが最初の関所

```
node scripts/honyaku-patch-build.mjs <置換表.json> <出力する指示書.json>
```
- **ライブから現在の本文を取り直して**置換を当てる（手で転記しない）
- **置換元がちょうど1回出てこなければエラーで止まる。** 0回でも2回でも止まる
- 置換後に置換元が残っていないことを確認する
- 同じ欄に2つ以上の置換があるときは、**前の置換結果に重ねる**

★この関所は実際に何度も事故を止めている（打ち間違い・本文が変わっていた・仏語1件が0回 等）。
**止まったら「置換表が悪い」ではなく「ライブが自分の想定と違う」を先に疑い、本文を取り直す。**

### ③ 計画を作る（書き込みなし）

```
node scripts/artist-i18n-update.mjs plan --file <指示書.json>
```
- 差分が全部表示される。**目で読む**
- **対象作家の全フィールドがバックアップに保存される**（apply の前に必ず存在する）
- 「2箇所の不一致」は artist_i18n と個別フィールドのズレ。**反映前と反映後で件数が増えていないこと**を確かめる

### ④ 適用する

```
SHOPIFY_ALLOW_WRITE=1 node scripts/artist-i18n-update.mjs apply --plan <plan_*.json> --yes > <ログファイル> 2>&1
```

**★apply の出力を `grep -c` 等のパイプに通さない。**
出力を食われて成否が読めず、二重実行の原因になる（実際に起きた。CASが書き込み前に止めた）。
**必ずファイルへリダイレクトし、あとから読む。**

apply が自分でやっていること：
- **楽観ロック（CAS）**＝計画作成時のライブ値と、apply 直前のライブ値が違えば**上書きせず停止**
- **1作家につき1回の `metaobjectUpdate`** で artist_i18n と個別フィールドを同時に送る（片側だけ更新される状態を作らない）
- **反映後に別クエリで取り直して完全一致を検証**。一致しなければ停止
- 更新しないフィールドは部分更新で保全（`values:` に変えると未指定フィールドが全消去される。**絶対に変えない**）

### ⑤ ライブで自分でも確かめる（applyの報告を鵜呑みにしない）

全件について「**新しい文が入っていること**」と「**旧い文が残っていないこと**」を、
**ライブを取り直して**確認する。件数を出す。

---

## ★本番データを書き換える直前に、必ずライブを取り直す

計画を作った時点のライブと、適用する時点のライブは**同じとは限らない**。
他のターミナルが同じ作家を直しているかもしれない。

- `honyaku-patch-build.mjs` が**生成時にライブから取り直す**ので、②→④を続けて行えば自動的に満たされる
- **時間が空いた計画は当てない。作り直す**
- 不要になった計画は消さず、`_STALE_適用しないこと_` を頭に付けて理由を書いて残す

## Vault のローカル正本を直すとき

**Edit で直接上書きしない。**
```
node scripts/vault-file-update.mjs <対象ファイルの絶対パス> <新内容ファイルの絶対パス> [ラベル]
```
バックアップ（`C:\Vault\ARTS-RESPECT\_backups\_auto\<ファイル名>\<日時>_<ラベル>`）＋書き込み＋
読み戻しSHA-256照合を**1回の呼び出し**で行う。バックアップを取る/取らないを判断させないための仕組み。

## git（記録を push するとき）

1. `git pull` してから書く
2. **追記は末尾に足すだけ。** 共有ファイルの全文読み込み→全文書き出しをしない（他ターミナルの追記が消える）
3. `git check-ignore -v <パス>` で無視されていないことを確かめる
4. **`git add` には明示的なファイルパスだけを渡す。** `git add .` / `-A` / ディレクトリ丸ごとを使わない
   （共有リポジトリで他ターミナルの未コミット作業を巻き込む事故が起きている）
5. `git commit -m "…" -- <同じ明示パス>`
6. `git show --name-only` を**全部読む**（自分のファイルだけが入っていること、実データ・秘密値が混ざっていないこと）
7. push 後に `git log -1 --format=%H` でフルSHAを取り、**SHA固定の blob URL を1行出す**

## 承認が要る一線

`SHOPIFY_ALLOW_WRITE=1` は本来「明示承認が要る一線」。
**日課の是正など、あらかじめ承認された作業の範囲では都度の確認を取らずに実行してよい。**
範囲外（本番テーマへの法的文書の反映・決済の本番設定・不可逆な削除・代表のログインが要る操作）は
**必ず事前に確認する。**
