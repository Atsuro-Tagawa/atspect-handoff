# 手順：作家ページの8言語データを更新する（artist_i18n ＋ 個別フィールドの同時更新）

対象ツール＝`scripts\artist-i18n-update.mjs`（2026-07-31 新設・システム開発T）
この1枚だけ読めば使えるように書いています。**リサーチTはJSONの指示書を書いて渡すだけで済みます。**

---

## 1. なぜこのツールが要るのか（30秒で）

Shopifyの作家データ（metaobject `artist`）は、多言語テキストを **2箇所に二重に持っています**。

| | 中身 | 言語 |
|---|---|---|
| ①個別フィールド | `bio_ja`…`bio_es` / `message_ja`…`message_es` / `genre` `location` `statement` `collection_places` `groups` `masterworks_text` | bio・messageは7言語（**deが無い**）、それ以外は日本語のみ |
| ②`artist_i18n`（JSON） | `role` `location` `statement` `bio` `viewpoint` `collection` `groups` `masterworks` ＋ `name_kana` | **8言語**（ja/en/zh_cn/zh_tw/ko/fr/es/**de**） |

作家ページのテーマは**両方**を読みます（SSRのHTMLは個別フィールド、そのあとJSが `artist_i18n` で上書き描画）。
**片方だけ直すと、同じ作家の中で言語によって表示が食い違います。** だから同時に直す必要があります。

また **`viewpoint`（功績）は `artist_i18n` にしか存在しません。** 従来の `artist-csv-sync.mjs` は
`artist_i18n` を「別途設計が必要」として除外していたため、viewpoint は一切直せませんでした。
このツールがその経路です。

## 3. 指示書（JSON）を書く

ファイル名は自由。置き場所も自由（例：`scratch\artist-i18n\20260801_是正.json`）。

```json
{
  "note": "何のための更新かを一言",
  "enteredBy": "リサーチT",
  "enteredDate": "2026-08-01",
  "updates": [
    {
      "name": "二川 幸夫",
      "handle": "futagawa-yukio",
      "reason": "一次資料（GA JAPAN 2013年追悼号）で確認。必須項目です",
      "i18n": {
        "viewpoint": { "ja": "…", "en": "…", "zh_cn": "…", "zh_tw": "…", "ko": "…", "fr": "…", "es": "…", "de": "…" },
        "collection": { "ja": "東京都写真美術館、GA gallery", "en": "Tokyo Photographic Art Museum, GA gallery" },
        "role": { "ja": "建築写真家" },
        "name_kana": "ふたがわ ゆきお"
      },
      "flat": {
        "masterworks_text": "日本の民家、GA"
      }
    }
  ]
}
```

### 書き方のきまり

| 項目 | 説明 |
|---|---|
| `name` | 作家名。姓名の間の空白は有無どちらでも一致します（「鈴木 千賀子」＝「鈴木千賀子」） |
| `handle` | URLスラグ。**同名の作家がいる場合は必須**。`name` と両方書くと取り違え防止の照合が働きます |
| `reason` | **必須**。空だと弾かれます（監査のため。実行ログに残ります） |
| `i18n` | 更新したい項目。**書いた言語・書いたキーだけ**が変わります。書かなかったものは元のまま |
| `flat` | **`artist_i18n` に対応物が無い個別フィールドだけ**が書けます（`masterworks_text` / `category` / `book_history`）。`bio_ja` や `genre` のように `artist_i18n` と対になっているフィールドは**`flat` では指定できません**（弾かれます）。そちらは `i18n` に書けば自動で両方に入ります |
| 空にしたい | 値に `null` を書く（`"ja": null` → 2箇所とも空文字になります） |

**使えるキー**＝`bio` / `message` / `role` / `location` / `statement` / `collection` / `groups` / `viewpoint` / `masterworks` / `name_kana`

★**「個別フィールドだけを直す」ことは、このツールでは意図的にできません。** `bio_ja` だけを直せてしまうと
`artist_i18n.bio.ja` と食い違うためです（Codexの独立レビューで指摘され、2026-07-31に塞ぎました）。
個別フィールド側が間違っている場合も、`i18n` に正しい値を書いてください＝2箇所とも正しい値になります。
**使える言語コード**＝`ja` `en` `zh_cn` `zh_tw` `ko` `fr` `es` `de`（ハイフンではなく**アンダースコア**）

★`role` は画面上の「呼称」です。個別フィールド名は `genre` ですが、実測で対応するのは `role` です（名前で推測すると間違えます）。

## 4. 差分を確認する（dry-run・書き込みなし）

```bash
node scripts/artist-i18n-update.mjs plan --file scratch\artist-i18n\20260801_是正.json --label 是正
```

このとき次が起こります：

1. 指示書の形式を全部検査し、**1件でも不備があればその場で停止**（一部だけ実行はしません）
2. 対象作家を特定（見つからない・同名で一意に決まらない場合も停止）
3. **対象作家の全40フィールドをバックアップ**へ保存
   → `C:\Vault\ARTS-RESPECT\_backups\_auto\artist-i18n\<日時>_<ラベル>\backup.json`
4. 「現在 → 更新後」を1項目ずつ画面に表示
5. 「2箇所の不一致：反映前 N件 → 反映後(見込み) M件」を表示
6. 計画ファイルを `scratch\artist-i18n\plan_<日時>_<ラベル>.json` へ保存

**表示された内容が意図どおりか、ここで必ず目で確認してください。** ここまでは何も書き換わっていません。

## 5. 反映する

```bash
set SHOPIFY_ALLOW_WRITE=1 && node scripts/artist-i18n-update.mjs apply --plan scratch\artist-i18n\plan_<日時>_是正.json --yes
```

- `SHOPIFY_ALLOW_WRITE=1` は**田川代表の明示承認が必要な一線**です。AIが独断で付けてはいけません。
- 実行時の安全装置：
  - バックアップファイルの存在を確認できなければ実行しない
  - **楽観ロック**＝計画を作ったあとに誰かがライブ側を直していたら、上書きせず停止
  - **1作家＝1回の `metaobjectUpdate`** で `artist_i18n` と個別フィールドを送る
    （2回に分けないので「片側だけ更新された状態」が原理的に発生しません）
  - 反映後に**別クエリで取り直して**完全一致を検証。一致しなければ停止
  - 更新前後の全フィールドを実行ログ `scratch\artist-i18n\apply_log_<日時>.jsonl` に残す

## 6. 失敗したら戻す

```bash
set SHOPIFY_ALLOW_WRITE=1 && node scripts/artist-i18n-update.mjs restore --backup "C:\Vault\ARTS-RESPECT\_backups\_auto\artist-i18n\<日時>_<ラベル>\backup.json" --yes

# 一部の作家だけ戻す
... restore --backup <path> --yes --handle futagawa-yukio,yokoyama-taikan
```

戻したあと、**全フィールドがバックアップと完全一致したことを機械で確認**してから完了と表示します。
一致しなければエラーで止まります。

### restore の安全装置と、その限界（Codexの独立レビューを受けて2026-07-31に強化）

- `apply` は書き込んだ直後の全フィールドを `applied.json`（バックアップと同じフォルダ）へ残します。
  `restore` はこれと現在のライブ値を突き合わせ、**`apply` のあとに誰かが直した形跡があれば停止**します。
  そのまま戻すと他の人の正しい修正まで巻き戻してしまうためです。承知のうえで戻すときだけ `--force` を付けます。
- **画像などの参照フィールド（`portrait` `hero_image` `masterpiece_*`）は書き戻しません。**
  これらが変わっていた場合は「復旧できないフィールドあり」と表示して停止します（Shopify管理画面での対応が必要）。

### ★正直に書く：完全なロールバックが保証できない場合

Shopifyの更新は**作家1名ごと**であって、複数名をまとめた取り消し（トランザクション）はできません。したがって：

| 失敗のしかた | 起きる状態 | 対処 |
|---|---|---|
| 更新のGraphQLがエラーを返した | ツールが**実測して**「何が変わったか」を表示します（変更0なら復旧不要） | 表示に従う |
| 書き込みは成功したが読み戻し検証に失敗 | **書き込みは実行済み**＝一致した項目は新値のまま残る中途半端な状態 | 表示される `restore` コマンドで戻す |
| 複数名の途中で失敗 | 完了済みは新値／失敗中は不定／以降は旧値 | `restore` は対象全員ぶんのバックアップを持っているので全員戻せる |
| 書き込み後・検証前にネットワーク断や強制終了 | ライブは更新済みだがログに記録が残らない | `show` / `verify` で現物を実測してから `restore` |

**「1名ずつ実行する」のが最も安全です。** 大量に流す前に、必ず1〜数名で試してください。

## 7. ★このツールで更新**できない**もの（正直に）

| できないこと | 理由・代わりの手段 |
|---|---|
| `handle`（URLスラグ）の変更 | リダイレクト設計が必要。別作業 |
| `name_ja`（作家名） | 照合キーのため。変更は別作業 |
| 画像（`portrait` `hero_image` `masterpiece_1_image` `masterpiece_2_image`） | 対象外。Shopify Files側の作業 |
| `is_listed`（公開フラグ） | 対象外 |
| 作家の**新規作成・削除** | 既存レコードの更新のみ。新規登録は別フロー |
| `masterworks` の自動ミラー | 実データが**配列形式599件／言語オブジェクト形式25件**に割れており、配列から `masterworks_text` を「、」連結で導出しても一致率93.1%（557/598）＝41件を取り違える。**`i18n.masterworks` と `flat.masterworks_text` を両方明示**してください |
| `bio_de` / `message_de` の個別フィールドへの書き込み | **そもそも存在しません**（metaobject定義が40/40で上限に達しており作れない）。deは `artist_i18n` にのみ入り、テーマもそこを読みます＝これで正常です |
| `collection` `groups` `role` `location` `statement` の**日本語以外**の個別フィールド | 存在しません（元から日本語のみ）。多言語は `artist_i18n` が唯一の置き場です |
| CSV正本（`artists_master_cleaned.csv`）への反映 | このツールはShopifyのみを更新します。CSV側は別途手で直してください |
| 同名作家の自動判別 | できません。`handle` で指定してください（`plan` が停止して知らせます） |

## 8. 現状の実測メモ（2026-07-31・625件）

- **2箇所は完全には一致していません。**
  `verify`（全625名）の実測＝**206件**の不一致。内訳＝`groups.ja` 122／`collection.ja` 38／
  `bio.ja` 8／`bio.en` `bio.fr` `bio.es` 各6／`location.ja` 5／`statement.ja` 3／`role.ja` 2／
  `bio.zh_cn` `bio.zh_tw` `bio.ko` 各1／`message.*` 各1（計7）。
  これに加えて、`verify`の対象外にしている`masterworks`が**594件**（`masterworks_text`に値があり
  `artist_i18n.masterworks`側が未設定）あり、**合わせると800件**です。
  **これは「差分の候補一覧」であって「直すべき」という判断ではありません。** どちらが正しいかはリサーチTの判定が要ります。
  一覧CSVは`verify`実行時に`scratch\artist-i18n\inconsistencies_<日時>.csv`へ出ます。
- ミラー表（どの個別フィールドがどのi18nキーに対応するか）は、625件の総当たり一致率で機械的に確定させたものです
  （`bio_zh_tw`↔`bio.zh_tw` 100.0% ／ `genre`↔`role.ja` 99.7% ／ `collection_places`↔`collection.ja` 99.6% など）。
  スクリプト冒頭の `MIRROR` にすべて記載しています。**名前が似ている順で推測すると間違えます。**
- ドイツ語ページで「収蔵先」等が日本語のまま出るのは、`collection.de` 等が空だからです（テーマは空なら上書きしない）。
  **このツールで `de` を入れれば直ります。**

## 10. Codexによる独立レビュー（2026-07-31・2観点）

| 観点 | 結果 |
|---|---|
| ①2箇所を確実に同時更新するか | **欠陥を検出。修正済み。** `flat` でミラー対象の個別フィールドを単独指定でき、`{i18n:{}, flat:{bio_ja:"新"}}` や `{i18n:{bio:{ja:"A"}}, flat:{bio_ja:"B"}}` で2箇所を食い違わせられた。ミラー対象は `flat` で書けないようにし、指示書検証・`buildUpdate` の二重で弾くようにした |
| ②失敗時にデータが壊れないか | **5点を修正。** (1)更新エラー時に「書き込みは行われていません」と根拠なく断定していたのを、実測して報告する形に変更 (2)`restore` に楽観ロックが無く第三者の変更を巻き戻す問題→`applied.json` による検出を追加 (3)バックアップは存在確認のみだった→中身（`store`・`artists`・`gid`・`artist_i18n`のJSON妥当性・計画対象が全員そろっているか）を検証 (4)書き戻せない参照フィールドを他の不一致と区別して報告 (5)検証失敗時に「書き込みは実行済み＝中途半端な状態」と明示し、復旧コマンドを提示 |

Codexが挙げたうち「複数作家の途中失敗」「ネットワーク断」「トランザクション不在」は、
Shopify APIの仕様上コードでは解消できないため、**修正ではなく §6 の表として正直に文書化**しました。
